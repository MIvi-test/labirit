# Labirit

Генератор лабиринтов на C для Linux. Поддерживает алгоритмы Прима, DFS, растущего дерева, Уотсона, двоичного дерева и рекурсивного разделения.

Нужны GNU Make и компилятор C с поддержкой C23.

## Запуск

```bash
make
```

Команда собирает программу и выводит лабиринт 10×10. Чтобы выбрать алгоритм, размер и seed, сначала соберите программу, затем запустите её с аргументами:

```bash
make compile
./main dfs 20 12 42
```

Формат: `./main [алгоритм] [столбцы] [строки] [seed]`. Если seed не задан, он выбирается случайно. Для списка аргументов используйте `./main --help`.

## Другие команды

```bash
make benchmark  # запустить бенчмарки; JSON-файлы результатов перезаписываются
make test       # собрать и запустить тесты
make clean      # удалить собранные программы
```


# УНИКАЛЬНАЯ ИНФОРМАЦИЯ О ВЕТКЕ

В данной ветке было реализовано х10 ускорение работы подсчёта полного бенчмарка.

## Мультипроцессорность

В первоначальном коде все подсчёты были последовательны, поэтому суммарное время на подсчёт метрик для одной генерации(из 2280) складывалась математически из суммы работы каждой метрикии
Все подсчёты и состояния в функциях подсчёта метрик основывались прежде всего локальные состояния, поэтому было решено внедрить мультипоточность. Это привело к тому, что теперь количество времени на подсчёт метрики определяется не как сумма, а как max(func_metrics). На практике, очевидно, это max(ASPL,entrophy), что сократило время примерно в 2 раза.
Интересно, что в итоговой версии реализация мьютекса для синхронизации оказалсь не нужной. Всё же была найдена реализация через thread_join, чтобы процесс записи в json был только после отработанных всех процессов.
В неудачной попытке реализации через мьютекс был поймана поймана ошибка(race condition) когда глобальную переменную инкрементировали два потока, и поэтому случилось зависание.


## Мультипроцессорность

Реализации мультипоточности для каждой func_metrics оказалось недостаточно для комфортного использования подсчёта. Хоть каждый процесс бенчмарка и запускает 5 потоков, но они внутри неодинаково тяжелые в подсчётах, поэтому через btop можно явно видеть, что почти всё время работает 3 потока, то есть 2 потока вычисляют, один на функцию бенчмарка. Делать мультипоточность для всех алгоритмов является плохой идеей, так как известно заранее, что функцию rand, которая полагается на ГЛОБАЛЬНОЕ состояние ведет к race condition и сидеть изобретать методы синхронизации почти всегда приведут к... Почти последовательной работе многопоточности. Реализация внутренней rand функции для генерации лабиринтов является плохим выбором, ведь это влияет на качество лабиринтов, а значит в подсчёте метрик генерации это недопустимо. Бенчмарк не должен влиять на качество лабиринтов.
Так как при подготовке было решено, что конечная реализация только под линукс, то было решено прийти к методу через fork() + execve(). Именно мультипроцессорность позволить для rand + seed позволит корректно оптимизировать работу бенчмарка, не влияя на топологические качества генерируюмых обьектов. 7 процессов по 5(3) потоков(а) создают явную нагрузку на процессор, около 70% процессорного времени, что значит **значительное** ускорение выполнения бенчмарка.
### тонкости реализации

Так как мультипроцессорность полагается на копирования самого себя, то чтобы не было бесконечного геометрического увеличения количества процессов-детей, было сделана проверка
после fork() на то, что код работает уже относительно ребенка, а не родителя(-1 код если до сих пор родитель). 

Следующий цикл отвечает за корректное завершение процессов детей. Для обработки сигналов(не только успешных) пришлось гуглить stackoverflow.


### Выигрыш по времени
вызов time ./benchmarks дал очень явную статистику
Executed in  610.18 secs    fish           external
   usr time   96.04 mins    0.38 millis   96.04 mins
   sys time    0.02 mins    1.12 millis    0.02 mins

Где написано, что общее процессорное время всех процессов и поток это 96 минут. То есть в среднем около 9.4 логического CPU использовалось в среднем.
Реальное время работы составило **610 секунд**. То есть 10 минут. Это огромнейший выигрыш.

## Результаты

Суммарно было сокращено примерно в 12 раз скорость подсчёта бенчмарков. Главное бутылочное горлышко было это последовательное вычисление независимых метрик, использование одного потока на многоядерном процессоре и cpu ожидание своего кванта времени. Итоговая скорость подсчёта времени работы бенчмарка это 10 минут 10 секунд.
